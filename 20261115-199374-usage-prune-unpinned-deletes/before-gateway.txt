# /usage cost through an isolated Gateway after deleting 100 of 5000 transcripts (24 months each), before the fix.
# Entry point: chat.send {"message":"/usage cost"} -> handleUsageCommand -> formatSessionUsageCostSummary
#   -> loadCostUsageSummary -> full refreshCostUsageCacheForAgent (no sessionFiles, so it prunes)
#   -> usageCache.prune writer transaction (operation=session-cost-usage.rollup.prune).
# State: the same prepared state as the refresh media (cache built by a real refresh with the head
#   driver at the Gateway's live path, cache_entries planner statistics set to the one-row values,
#   moved to a pristine directory). Each run restores the database and config as copies and the
#   transcripts as hard links (the usage checkpoint records device and inode), starts the Gateway
#   (own state directory, loopback port, token auth, channels/providers/cron off; no model is called:
#   the /usage reply is gateway-injected), waits until the Gateway's process group is idle, opens
#   the agent database writer with three sessions.patch writes, deletes 100 transcripts, then sends
#   /usage cost while a foreground sessions.patch probe writes the same agent database every 10 ms.
# steps.log "rows" lines are read-only SQLite reads of cache_entries between steps (rollupLastWrite
#   unchanged = no session was rescanned). EXPLAIN plans come from an observer preload that runs
#   EXPLAIN QUERY PLAN for each cache_entries DELETE in worker threads; no product code is changed.
# Runtime: both sides ran built dist under Bun 1.4.4 through scripts/run-node.mjs gateway run.
#   An observer preload (reservation-preload.cjs) subscribed to the agent-database reservation
#   diagnostic channel; it loaded in each Gateway thread but recorded no channel message on either side, so its file is
#   not a measure ("reservations before delete" counts only its per-thread "loaded" records).
# Hold measure: the product's own state-log lines, shown raw. "slow agent database reservation"
#   with workerOperations ["usageCache.prune"] is the prune's writer hold (writerExecutionMs);
#   "slow SQLite session write" with holderAtEnqueue usageCache.prune is a sessions.patch that
#   queued behind it (queueWaitMs); "slow SQLite transaction hold" is the prune transaction
#   (threshold 1000 ms). Both sides log at the same thresholds. The 18:07:34 reservation line
#   (pid 43240, open/database.prepareWrite) is in the restored log file from the template build,
#   before every run; it is not part of the run.
# On this state the /usage cost reply is cut off by the 360 s reply watchdog on both sides. It is
#   attributed to the read-only sessions.usage.summary transaction that follows the refresh
#   (unchanged by this change): at 500 sessions on the head, under the same one-row statistics,
#   that read held 44 s and 61 s and the request replied in 44.8 s (run smoke8); without the
#   statistics the request replied in 0.7 s (run smoke9, which has no row counts). At 5,000
#   sessions it did not finish before the watchdog and no summary line was logged. For the same
#   reason the follow-up usage.cost request hits its 15 s budget, so retained usage is shown by the
#   rows lines.
# Time stamps: steps.log lines are UTC; Gateway and state-log lines and the probe times below are
#   local time (+09:00). ANSI color codes were stripped from the command output.
# summarize.mjs prints the figures from the files shown; probesDuringRequest are the sessions.patch
#   round trips that overlapped the request. Omitted in place: the client's chat.history output
#   (the request and final chat event are shown), the 26k raw probe records (summarized), and the
#   final payload's message.idempotencyKey (equal to runId).
# Placeholders: <checkout>, <state-dir>, <state-root>, <proof-dir>, <home>, <loopback>, <port>, <host>.
